The Phoenix Mental Model

Seven ideas that make the rest of this page predictable. Get these right and most of Phoenix's design choices stop looking arbitrary; get them wrong and almost every subsystem reads as strange.

ClariFI Phoenix is a distributed financial-data platform. Apache Ignite is the third-party in-memory data grid it is built on — it is the technology, never the product. Each card below states the idea in plain language first, with the Java and configuration specifics on the secondary line.

The seven durable ideas

1 — Phoenix is a cluster, not a server

It is a stateless API tier over a stateful in-memory compute grid, with work routed to the data by affinity. That is the accurate description: not a monolith, not microservices. One codebase produces one container image that runs in one of six modes.

API servers run ServerApp; data nodes run NodeApp; Launcher picks between them from the RUN_MODE environment variable.

src/main/java/com/clarifi/phoenix/ashes/Launcher.java, src/main/java/com/clarifi/phoenix/ashes/server/ServerApp.java, src/main/java/com/clarifi/phoenix/ashes/node/NodeApp.java — see Architecture Overview

2 — The API server holds no data

The tier that answers HTTP requests owns nothing. It is an Ignite thin client, not a cluster member, so it cannot execute arbitrary compute directly. Two cluster-singleton bridge services exist specifically to compensate.

It calls Ignition.startClient(…). ComputeProxyService submits, polls and cancels an IgniteCallable by handle; ClusterAdminProxyService covers atomics, affinity lookups, baseline topology and cache metrics. Map/reduce ComputeTasks bypass both and use the thin client's native named-task API.

src/main/java/com/clarifi/phoenix/ashes/server/ServerApp.java, src/main/java/com/clarifi/phoenix/ashes/node/ComputeProxyServiceImpl.java — see Services & Distributed Compute

3 — Computation travels to the data

Phoenix does not pull rows to a calculation engine. It sends the calculation to the machine that already holds the rows, and only small partial results come back. This is the mechanism behind the platform's core performance claim.

TransformOrchestratorTask.map() calls ignite.affinity(TIMESERIES_METADATA_CACHE_NAME).mapKeyToNode(…) to group issues by owning node, then creates exactly one NodeTransformJob per node, each reading only local segments. CreateLinkedBasketTask carries a source comment stating outright that nothing large ever crosses the Ignite wire.

Rationale stated in source — minimise data movement. See Architecture Decision Log.

4 — The cache set is the schema

Phoenix has no relational database of its own. Its schema is the set of Ignite caches declared in a single file, which is also the only place in the codebase permitted to create one. There are no migration scripts and no DDL, because there is no relational database to migrate.

Caches is 449 lines holding 38 CacheConfiguration declarations; CacheCreationEnforcerTest is an ArchUnit rule that fails the build if any other class calls createCache or getOrCreateCache.

src/main/java/com/clarifi/phoenix/ashes/common/Caches.java — see Data Model & Cache Catalog

5 — Persisted schema is append-only, and the build enforces it

This is the single most important constraint on changing Phoenix. Fields on persisted classes are never removed or renamed, enum constants are never deleted and their byte codes are never reused, and golden binary payload fixtures are never hand-edited.

Twelve concrete enforcer tests fail the build on violation. Practically: a business change that implies removing a field is not a code change, it is a migration requiring architect approval.

DESIGN.md — see Data Model & Cache Catalog and Business Rules & Constraints

6 — The vendor databases are the systems of record

The authoritative data lives outside Phoenix, in external S&P Global SQL Server feed products such as Xpressfeed (Compustat) and Capital IQ. Phoenix is a read-only consumer of its upstream systems and never writes back to them.

Every JDBC connection is opened read-only, with a 30-minute maximum lifetime, leased from a per-host slot budget under per-user credentials.

docs/data-catalog/ReadMe.md, src/main/python/BOOTSTRAP.md — see External Integrations and Data Access Layer

7 — Working state is disposable; reference state is durable

Data sessions and their results are deliberately throwaway — everything they hold can be recomputed — while the reference universe, catalog, baskets and user records survive restarts. The split is a design decision, not an accident of storage.

Tier 1 ephemeral caches (DataSessions, DataSessions[Results]) are wiped by EphemeralCacheClearer on cluster activation, so their schema cannot rot. Security Master, catalog, baskets and users are held indefinitely under native persistence; series and point-in-time segments are indefinite but reloadable.

See Data Lifecycle and Data Model & Cache Catalog

What Every Engineer Should Know

The eleven facts that most often decide whether a change is correct or merely compiles. Each one is load-bearing somewhere in the codebase, and several are enforced by tests that fail the build.

Hover a confidence badge for the evidence wording used in the source. Where the repository states a rationale it is recorded as stated; where it does not, the fact is recorded without inventing a motive.

The API server is a thin client, and two bridge services exist because of it

The API tier calls Ignition.startClient(…), holds no data and owns no local Ignite node, so it cannot execute arbitrary compute directly. ComputeProxyService submits, polls and cancels an IgniteCallable by handle; ClusterAdminProxyService covers atomics, affinity lookups, baseline topology and cache metrics. Map/reduce ComputeTasks bypass both and go through the thin client's native named-task API.

Every cache is declared in one file, and an ArchUnit rule enforces it

Caches is 449 lines holding 38 CacheConfiguration declarations, and it is the only place in the codebase permitted to create a cache. CacheCreationEnforcerTest fails the build if any other class calls createCache or getOrCreateCache. Known enforcement gap: the rule cannot see XML/Spring or SQL-DDL cache creation.

src/main/java/com/clarifi/phoenix/ashes/common/Caches.java, DESIGN.md HIGH

Persistence is three schema-first tiers, and the persisted schema is append-only

Tier 1 @IgniteEphemeral uses native Ignite serialization for throwaway compute state; Tier 2 @ProtobufHybridShell wraps a Protobuf byte[] in an Ignite shell class for standard entities; Tier 3 @CustomBinary is hand-rolled ByteBuffer bit-packing, used for Security Master attribute values only. Fields are never removed or renamed, enum byte codes are never reused, and golden binary fixtures are never hand-edited — twelve concrete enforcer tests fail the build on violation.

Tier 2 shells must be generated by generateHybridShells, never hand-written. Open gap: no automated Protobuf backward-compatibility check exists, and Tier 3 has HIGH schema risk with no schema-diff tool at all. DESIGN.md — see Data Model & Cache Catalog

Routes are hand-registered; there is no declarative route registry

Routes are registered imperatively inside ServerApp.completeStartup() using Undertow's Handlers.routing() builder, grouped by comment banners, across roughly lines 715–995. Each functional area exposes a small static factory class — UsersV3, SecurityMasterV3, DataCatalogV3, DataSessionsV3 — whose methods build the standard decorator stack.

src/main/java/com/clarifi/phoenix/ashes/server/ServerApp.java — see Backend Runtime

OpenAPI documents the API; it does not drive routing

The fragment tree under swagger/paths/ and swagger/schemas/ is the nearest thing to a declarative registry, but it documents rather than drives routing — which is exactly why the two drift, and why nothing fails when they diverge. The assembler does validate fragment syntax at startup and refuses to boot on a malformed file; it cannot detect a fragment that describes something the router does not serve.

Roughly 95 registered method × path operations against 51 OpenAPI paths and 62 shared schemas. OpenApiStartupAssembler — see API Catalog & Explorer

Authentication is default-deny, and an unknown path gets a bare 404

AuthMiddlewareHandler rejects anything not under /api, /api-legacy or /admin and not in the public exact or prefix lists with a bare 404 — deliberately, to avoid confirming what exists to a prober. A missing, unparseable or expired token yields 401; an empty permission set yields 403 except for /api/version; any /admin path additionally requires ADMIN_READ.

Tokens are resolved from the X-Auth-Token header first, then the PHX_AUTH cookie, and validated cluster-side by UsersService. See Authentication & Authorization

There is no SPA and no frontend build

No React, Angular or Vue; no package.json, bundler, TypeScript or npm build step anywhere outside the vendored Swagger UI distribution. The entire hand-written client-side codebase is two JavaScript files and two stylesheets. Phoenix's real interface is its HTTP API; the served pages are operator tooling.

src/main/resources/static_web/ — see Frontend & User Interface

Cluster-wide metrics collection is currently a stub

ServerApp.fetchHttpRequestMetrics() and fetchDatabaseUsageMetrics() return empty maps and log a warning; a source TODO explains that per-node collection was not migrated for the thin-client API server. The five-minute poll that fills the one-hour and 24-hour history views is therefore a no-op, and the monitoring pages show only the metrics of the API server instance you happen to be talking to.

A second recorded gap: the memory page reports one arbitrary node's heap rather than a cluster total (MonitoringHandler TODO). HIGH — see Observability

Five endpoints are wired to return 501 by design

They are registered in the route tree but answer 501: DELETE /api/dataExport/drop/{userId}/{sessionId} (a bare not-implemented response via DataSessionsV3.delete), GET /api/securityMaster/issues and GET /api/securityMaster/holidays (both UnderDevelopmentHandler; the latter is distinct from the working /api/holidays), DELETE /api/securityMaster/attribute/{attributeId} and DELETE /admin/securityMaster/attribute.

See API Catalog & Explorer and Error Handling

Peer class loading is disabled

It is explicitly off in both applications. It is a premise of the whole persistence contract — classes must already exist on the node that deserialises them — and it closes a large remote-code-execution surface.

DESIGN.md HIGH — see Architecture Decision Log

Enum identity is a stable byte code, because Ignite writes ordinals

Every enum in com.clarifi.* must implement PersistedEnum with a stable byte code: BinaryWriterExImpl.writeEnum() always emits ordinal(), and Binarylizable or a registered serializer on the enum is silently ignored. A persisted class therefore never holds a raw enum field — it holds a boxed Byte code with hand-written typed accessors, boxed rather than primitive so that a null is not masked by an autoboxed zero.

A raw EnumSet must never be persisted either — its bit-mask is keyed by ordinal, so reordering the enum would silently remap the set; sets are stored as a sorted byte[] of codes. Both rules are enforced by PojoComplianceEnforcerTest; the authoritative constant list is src/test/resources/payloads/ignite/golden_enum_codes.properties. HIGH — see State Machines & Enums

Read DESIGN.md before touching any cache, payload, enum, compute task, service or listener

Its rules are not style guidance — they fail the build. AGENTS.md is the canonical contributor rule set, INDEX.md says who owns a subsystem and what constrains changing it, and src/test/java/…/persistence/README.md carries the rationale with worked examples and the known enforcement gaps.

Things That Can Surprise You

Twelve places where a reasonable first assumption is wrong. Each is drawn from the same source evidence as the rest of this page; reading them now is cheaper than rediscovering them during an incident.

The HTTP tier

Looks like a conventional web service that owns its data and does its own work.

Actually the API server is an Ignite thin client, not a cluster member. It holds no data, owns no local Ignite node and cannot execute arbitrary compute directly — which is why the two cluster-singleton bridge services, ComputeProxyService and ClusterAdminProxyService, exist at all.

src/main/java/com/clarifi/phoenix/ashes/server/ServerApp.java, src/main/java/com/clarifi/phoenix/ashes/node/ComputeProxyServiceImpl.java — see Services & Distributed Compute

The OpenAPI document

Looks like the authoritative contract that defines what the server serves.

Actually it documents rather than drives routing, so nothing fails when the two diverge — and they do. The assembler validates fragment syntax at startup and refuses to boot on a malformed file, but it cannot detect a fragment describing an operation the router does not serve.

Roughly 95 registered operations against 51 documented paths; one fragment, paths/data-export/cancel.json, has no Java code at all. See API Catalog & Explorer

The :expression module

Looks like the home of the formula language, given the name.

Actually it contains only the compact date/year value types — CompactDate, CompactDateRange, CompactYear — and a small encoding utility. The formula grammar, parser and evaluation engine all live in the root project.

Engine: src/main/antlr4/ and src/main/java/com/clarifi/phoenix/ashes/transform/. The module also has its own PITest configuration, which is easy to misattribute. See Codebase Structure

“It's in common”

Looks like one shared module everyone means the same thing by.

Actually there are two. The :common Gradle module (com.clarifi.common.*, a JPMS module holding the annotations, the App lifecycle framework and the concurrency library) is entirely distinct from the root project's com.clarifi.phoenix.ashes.common package (Caches, Services, identity, database pooling and Security Master internals).

When someone says “it's in common,” ask which one. See Codebase Structure

DataSession.Status

Looks like an enum with one number behind each constant.

Actually it carries three. 1. id — the frozen public REST statusId, a sparse ladder (Initializing 0, Failed 2, Validated 4, Loading 8, Computing 12, Ready 16, Cancelled 32, Closed 48, TimedOut 64, ComputationError 96), sparse but not a bit mask. 2. code — the persistence byte, a dense 0–9 in declaration order. 3. ordinal() — explicitly documented as meaningless.

Confusing the REST id with the persistence code is an easy and costly mistake. src/main/java/com/clarifi/phoenix/ashes/common/DataSession.java — see State Machines & Enums

A 404 response

Looks like the record you asked for does not exist.

Actually it may be the default-deny gate. AuthMiddlewareHandler returns a bare 404 for any path not under /api, /api-legacy or /admin and not in the public exact or prefix lists — deliberately, to avoid confirming what exists to a prober. The same status is also used by handlers for a genuinely missing entity.

See Authentication & Authorization, Error Handling and Troubleshooting Guide

The monitoring pages

Looks like a cluster-wide view of traffic and resources.

Actually they show only the metrics of the API server instance you happen to be talking to. ServerApp.fetchHttpRequestMetrics() and fetchDatabaseUsageMetrics() return empty maps and log a warning — a source TODO explains per-node collection was not migrated for the thin-client server — so the five-minute history poll is a no-op. Separately, the memory page reports one arbitrary node's heap rather than a cluster total.

ServerApp, MonitoringHandler TODO HIGH — see Observability

Schedule delivery

Looks like a cron entry fires its occurrence exactly once.

Actually schedule delegation is explicitly at-least-once, not exactly-once: the same occurrence can fire more than once. Job bodies must be idempotent, keyed on schedule id plus fired timestamp. A job that ran twice is expected behaviour, not a defect.

docs/jobs/ReadMe.md — see Jobs & Schedulers

Session lifetime in a browser

Looks like one session length shared by browser and server.

Actually the browser's PHX_AUTH cookie is issued with a fixed one-hour maximum age (AUTH_COOKIE_MAX_AGE_SECONDS = 3600) while the server-side idle timeout is twelve hours (tokenIdleTimeoutSeconds: 43200). A browser session stops presenting a cookie long before the server would have expired the token; header-based clients using X-Auth-Token are unaffected.

Recorded as a potential area for review — an observation from configuration and source, not a reported defect. Whether the mismatch is intentional requires investigation. UNKNOWN — see Data Lifecycle and Investigation Areas

Point-in-time segment sizing

Looks like spanning multiple segments is an edge case worth handling defensively.

Actually it is the normal case. Point-in-time segments cap at 255 cells because their compressed-row index arrays are byte[], so a series of any real length spans several. That is precisely why PIT-01 (Critical) matters: the raw stream is not globally as-of-ascending once a series spans two or more segments.

docs/point-in-time/known-defects.md, cache PointInTime[SEGMENTS_DOUBLE] — see Data Model & Cache Catalog

MisfirePolicy

Looks like a single enum you can import without thinking.

Actually two enums share that simple name with entirely different constants — one in :common and one in the root project. An import fixed by the IDE is not necessarily the one you meant.

MEDIUM — see Investigation Areas

A timed-out chunk fetch

Looks like a timeout will surface as an error.

Actually this one returns a wrong answer instead. The repository records (PIT-16, rated Low but nasty) that a chunk-fetch timeout during a point-in-time computation returns a truncated matrix as if it were complete, rather than failing. Worth knowing when investigating a report of missing data.

docs/point-in-time/known-defects.md — see Error Handling

None of these is a reason to distrust the codebase

Most of the items above come from registers the team wrote about their own code — a 929-line point-in-time defect catalogue and a curated timeout audit. Only 13 TODO or FIXME markers exist across roughly 740 main-source files. The surprises are documented, not hidden; the cost is only to engineers who have not read them yet. See Investigation Areas.

Executive Overview

A one-minute orientation to what ClariFI Phoenix is and what it does, followed by a five-minute guided tour of the rest of this page. Everything here is derived from the repository itself; anything that could not be established from source is marked as such rather than guessed.

Naming: the application is Phoenix, not “Ignite”

The product is ClariFI Phoenix (README.md, INDEX.md). Apache Ignite is the third-party in-memory distributed data grid Phoenix is built on, not the name of the application. This page is filed as ignite-understanding.html by request, but throughout it “Phoenix” means the product and “Ignite” means the data grid.

One-minute understanding

What is Phoenix?

A distributed financial-data platform. A quantitative user defines a universe of securities and a set of data items, then pulls back large matrices of historical financial data — optionally transformed by formulas — far faster than querying the underlying databases directly.

Physically it is a cluster: a stateless HTTP API server plus one or more Apache Ignite data/compute nodes that hold the data in memory (with optional disk persistence) and execute calculations where the data already lives.

README.md, INDEX.md

What problem does it solve?

The authoritative financial data lives in external SQL Server databases — S&P Global feed products such as Xpressfeed (Compustat) and Capital IQ. Querying those directly, security by security and date by date, is slow and does not support interactive analytics.

Phoenix loads that data once into a distributed in-memory grid, indexes it by security and date, and then runs calculations on the nodes that already hold the data — so the data moves as little as possible.

docs/data-catalog/ReadMe.md, src/main/python/BOOTSTRAP.md

Who uses it?

Quantitative researchers and analysts, through the HTTP API and client tooling.

Platform administrators, for user/role/data-catalog management and Security Master rebuilds.

Operations and support staff, through the built-in monitoring pages.

Automated bootstrap and load-test tooling written in Python.

Business Problem & Purpose

Why Phoenix exists and what it does about the problem — separated clearly into what is genuinely established from the repository and what is reasonable interpretation.

The problem

The question a quantitative researcher needs to ask

“For these 3,000 securities, give me these 40 data items, monthly, for the last 25 years — and while you're at it, compute the 12-month compounded return and a cross-sectional rank.”

Where the authoritative data lives

In large external SQL Server databases — S&P Global feed products. The production client configuration lists roughly eighteen distinct source databases spanning Xpressfeed/Compustat, Capital IQ, SNL, Trucost, point-in-time financials, alpha signals, indices, ownership and transcripts.

config/prod/client.yaml

Why querying it directly does not work

Answering that question by querying those databases directly is impractical at interactive speed: it means thousands of parameterised round trips, repeated for every researcher and every re-run, against shared operational databases.

What Phoenix does about it

1. Load once, in parallel, into memory

Data items are defined as parameterised SQL templates against named data sources. Phoenix executes them across the cluster and stores the results as compact binary segments in Apache Ignite caches, keyed by security and date range.

.../server/resource/DataQuery.java, .../server/resource/DataSource.java

2. Move the computation to the data

Transform formulas are not evaluated on the API server. TransformOrchestratorTask uses Ignite affinity to map work to the node that already owns each security's data, and NodeTransformJob evaluates the formula there.

.../transform/TransformOrchestratorTask.java, .../transform/NodeTransformJob.java

3. Keep large result sets off the cluster wire

The design deliberately avoids shipping bulk data between nodes. The linked-basket loader streams JDBC rows straight into basket construction on the node holding the connection, with an explicit source comment that “nothing large ever crosses the Ignite wire”.

.../basket/compute/CreateLinkedBasketTask.java

4. Make reference data a first-class, pre-built asset

Rather than joining to identifier tables per query, Phoenix builds a Security Master — a replicated, densely packed in-memory dictionary of securities, identifiers, attributes and exchange calendars, rebuilt as a batch operation.

.../task/securitymaster/RebuildSecurityMasterTask.java

What would happen without Phoenix?

MEDIUM REASONABLE INTERPRETATION Based on the implementation, each consumer would be issuing their own parameterised SQL against the vendor databases, re-deriving identifier mappings, re-implementing return/moving-average logic, and re-querying the same history repeatedly. Phoenix centralises the data access, the identifier resolution, and the calculation library. The repository does not contain a written business case or product rationale, so this is inference from the implementation, not a documented fact.

Requires confirmation

Whether Phoenix replaces a specific predecessor system is not established from source. The name “ClariFI” is a known S&P Global quantitative-research product line, and the API server is titled “ClariFI Phoenix API” (src/main/resources/swagger/openapi.json), but the repository contains no migration notes, no legacy-system adapters and no decommissioning plan. Treat any claim of “replaces X” as unverified.

Users & Actors

Phoenix has comparatively few human roles but several important non-human actors. Authorisation is modelled as user → group → role → permission set.

How permissions actually work

A user's effective permissions are aggregated at login by BaseAuthenticator, resolved through their group and role definitions, and stored on the AuthenticatedUser as a set of permission codes (.../server/authentication/BaseAuthenticator.java, .../server/authentication/AuthenticatedUser.java).

Every request is then checked by AuthMiddlewareHandler: an empty permission set is rejected with 403, and any path under /admin additionally requires ADMIN_READ (.../server/handler/AuthMiddlewareHandler.java).

Enforcement detail: Authentication & Authorization.

Time Series & Point-in-Time — the two shapes historical data comes in Segment storage 19 verified defects

Business purpose

Two fundamentally different questions about historical financial data.

Time Series

“What was the value on each date?” A dated sequence of scalar values per security, per data item, per unit of account, at a fixed frequency and alignment. This is the shape of prices, volumes and most market data.

Point-in-Time

“What did we know on each date?” A matrix whose rows are as-of dates and whose columns are fiscal periods counted back from that as-of date. This captures restatement: a company's reported figure for a quarter can change months later, and a back-test that uses the restated figure is using information that was not available at the time.

Why this matters commercially. Point-in-time is the difference between a back-test that is honest and one that silently looks into the future. It is the more complex of the two shapes and, correspondingly, the one with a recorded defect register.

Step 3 — Only what is not already in memory is fetched, over a budgeted JDBC pool

Business: anything not already in memory is fetched from the vendor database. Anything already cached is reused — this is where the speed comes from.

Technical: status Loading. On each node, LoadSegmentsFromDatabaseTask (separate time-series and point-in-time variants) leases a pooled JDBC connection through BoundedDatabasePoolRegistry, compiles the data item's SQL template with SqlQueryTemplate, binds the date range and issue keys, executes it read-only, and packs the result into segments.

Connection budgeting: the registry enforces a slot budget per database host with four paths — reuse an existing pool, open a new one, evict the least-recently-used idle pool, or wait up to five seconds for a slot. Connections are read-only with a 30-minute maximum lifetime.

Failure: a SqlLoadFailure is recorded per data item; the external database being unreachable does not by itself abort every other item.

Step 4 — Raw output becomes the requested shape; the known point-in-time defects live here

Business: raw query output is turned into the shape the analyst actually asked for.

Technical: StoreTimeSeriesInLocalCacheTask / StorePointInTimeInLocalCacheTask (.../task/localcache/). For point-in-time this is the non-trivial step: a single-pass projection state machine converts the raw loaded stream into the as-of × period matrix.

Known defects concentrate on this step

This is the step the repository's defect register concerns. In particular, the raw stream is not globally as-of-ascending once a series spans two or more segments — and because segments cap at 255 cells, that is the common case, not an exotic one (docs/point-in-time/known-defects.md, PIT-01).

Step 5 — Derived measures are computed on the nodes that already own the data

Business: derived measures are computed.

Technical: status Computing. TransformOrchestratorTask maps one NodeTransformJob per node owning a subset of the requested issues, using Ignite affinity. Each node job reads its local segments in chunks, evaluates the formula dependency graph and returns a partial result; the orchestrator reduces the partials.

Failure: status ComputationError, with a structured error report captured on the session rather than a raw stack trace.

A timed-out chunk fetch looks like success

A chunk-fetch timeout currently returns a truncated matrix as though it were complete (PIT-16).

Step 6 — The matrix is flattened out to the client, and the session stays warm

Business: the analyst receives a flat matrix.

Technical: status Ready. Dedicated senders flatten and pivot the result — TimeSeriesFlatSender and PointInTimeFlatSender (.../server/dataexport/). The response is gzip-encoded by the outer middleware.

Side effects: loaded series identifiers are retained against the session so a follow-up POST /api/dataExport/query can query within it without reloading. The session is later Closed explicitly, or moves to TimedOut.

Outcome of Workflow A

Final result: a matrix of values keyed by security and date (time series) or by security, as-of date and period (point-in-time).

Database changes: segment and session caches written; no external database writes — Phoenix is a read-only consumer of the vendor databases.

Notifications: none; the client polls.

Workflow B — Security Master rebuild

Trigger

POST /admin/securityMaster/rebuild, or the bootstrap sequence.

Actor

Administrator or bootstrap client.

Preconditions

Attribute definitions exist; the reference-data databases are reachable.

  1. Rebuild requested
    The handler validates and dispatches; state moves from IDLE to RUNNING (RebuildState.Status).
  2. Reference data queried
    The configured exchange, holiday and weekend queries run against the reference database, alongside each attribute's own SQL or CSV source.
  3. Inactive generation populated
    Results are written into the inactive half of the double-buffered sm[…]_1 / sm[…]_2 cache pairs, using a bounded rebuild thread pool (16–32 threads in production).
  4. Generation swapped
    The active generation pointer flips, so readers see either the complete old universe or the complete new one — never a half-built mixture.
  5. Completion
    State returns to IDLE. Progress is observable at GET /admin/securityMaster/rebuild/status; a stuck rebuild can be cleared with POST /admin/securityMaster/rebuild/reset.

Duration

Business Rules & Constraints

These are the rules Phoenix actually enforces in code or configuration, not policy statements about it. Each is traceable; none are inferred — so this is the list that will push back when you design against the platform.

Access and identity

An empty permission set is a rejection

A token with an empty permission set is rejected on every path except /api/version.

Admin paths are gated twice

Every path under /admin requires ADMIN_READ at the middleware layer, in addition to any finer-grained check the individual handler performs — for example baskets require WRITE, and cross-user basket operations require ADMIN_BASKET.

Unknown paths reveal nothing

An unknown path that is not under /api, /api-legacy or /admin and is not explicitly public returns a bare 404 — deliberately, to avoid revealing server internals to probes.

Imported principals are immutable

Users, groups and roles imported from the security JSON files are marked locked and cannot be mutated through the admin API.

System accounts bypass rate limiting

System accounts — those holding SYSTEM_MONITOR, SYSTEM_CONFIGURE or SYSTEM_LOCKS — are exempt from rate limiting entirely.

Local authentication provider accepts any password for a user with no configured password

LocalFileAuthenticator treats a user with no entry in passwords.json as accepting any password. The shipped configuration for dev and prod uses Okta, not local (config/dev/server.yaml, config/prod/server.yaml), so this is a development-mode behaviour. Potential area for review if local were ever enabled outside development. Related: an unknown username falls back to a synthesised “Demo User”.

Data correctness rules

Partial success is the design

Issues and data items that do not resolve are recorded on the session as invalid lists; the rest of the request proceeds.

Transform order is derived, not declared

Transforms are topologically sorted from their formulas. A cycle produces Formula Error: Circular dependency detected in transforms.

Computation claim is exactly-once per session

A compare-and-set on the results cache elects one winner; losers receive 202 rather than duplicating the work.

Job delegation is at-least-once

Schedules can fire the same occurrence more than once; job bodies must be idempotent on schedule id plus fired timestamp.

Dates are representable only from 1901 to 2156

CompactDate stores a date as days since a 1901 epoch in a single char.

The Security Master swap is atomic from a reader's perspective

A rebuild writes the inactive generation and flips a pointer; readers never see a half-built universe. A continuous query on the settings cache is what makes the flip visible on other nodes — there is no polling or TTL fallback.

Engineering rules that constrain the business

Persistent schema is append-only, and the build enforces it

This is the single most important constraint on changing Phoenix. Fields on persisted classes are never removed or renamed; enum constants are never deleted and their byte codes are never reused; golden binary payload fixtures are never hand-edited. Twelve concrete enforcer tests fail the build on violation. Practically: a business change that implies removing a field is not a code change, it is a migration requiring architect approval. See Data Model & Cache Catalog and DESIGN.md.

The single most important architectural fact

Dependency Map

What depends on what, at runtime — and therefore what actually breaks when a given dependency is down. The coupling notes below are the part worth reading before an incident, not during one.

Everything below the API server runs inside the Ignite cluster.

What the map shows

  • Clients — browser, Python, Java, Bruno.
  • API server (thin client), with Okta to one side and the job + schedule engine to the other.
  • Bridge services — ComputeProxyService and ClusterAdminProxyService.
  • Ignite data nodes — services + compute, alongside the node-local cache (disk) and the 38 governed caches.
  • Backing stores — external SQL Server (read-only), AWS S3 for discovery, and native persistence (WAL + page store).

Coupling notes

API server → cluster: hard, even for auth

The API server depends on the cluster for authentication itself — token validation is a service call. If the cluster is unreachable, no request authenticates, so the server retries connecting in a background loop and /ready stays 503.

Data nodes → API server: none

Data nodes do not depend on the API server. They can be started, activated and operated entirely independently through the shell scripts.

Bridge services: single points of coupling

Both bridge services are single points of coupling for thin-client work. The compute proxy in particular is a cluster singleton.

External databases: runtime, not startup

External databases are a runtime dependency of loading, not of startup. The cluster starts and serves cached data with every upstream database down; only fresh loads fail.

Okta: logins, not sessions

Okta is a hard dependency of login in the shipped configuration. Existing tokens keep working, since validation is internal — so an Okta outage locks out new logins but does not evict active sessions.

S3: required to join the cluster

S3 is a hard dependency of node discovery in dev, staging and production. A node cannot join without it.

Backend Runtime

How the two server processes start, wire themselves up, handle a request and shut down. Almost every startup failure, auth surprise and shutdown ordering bug is explained by something on this page.

API server startup

Startup is a fixed sequence. Two of the steps are deliberately fail-fast, and one of them binds the only socket the process will ever bind.

  1. Parse arguments and verify the trust store
    Picocli reads --igniteConfig, --appName, --configDir, --httpPort and --httpHost. The SSL trust store is checked and a warning issued if missing.
  2. Assemble the OpenAPI document — fail fast
    Every fragment under swagger/paths/ and swagger/schemas/ is syntax-checked, all $refs are resolved recursively with cycle detection, and the merged document is serialised, gzipped and given a SHA-256 ETag. An invalid fragment stops the server from starting.
  3. Connect to the cluster, with retry
    A background loop calls Ignition.startClient, resolving addresses by s3, fixed or multicast, waits for the cluster to be ACTIVE and optionally auto-activates it. autoActivate is true in dev and false in production — production activation is a deliberate operator action.
  4. Bind the HTTP socket once
    Undertow is configured with worker and IO thread counts, buffer size, and idle / no-request / request-parse timeouts, all from http.*. The root handler is held behind an AtomicReference so the full handler tree can be swapped in later — and so a cluster reconnect never rebinds the socket.
  5. Complete startup
    Profilers, the cancellation registry, the linked-basket executor, the job scheduler and schedule service, the registered job-type providers, the chosen authentication provider, the security file import, the full route tree, the wrapped handler chain, the transform initialisation task, and the metrics poller. Finally ready is set, which is what /ready reports.

Shutdown

Shutdown is explicitly ordered, and deliberately not a JVM shutdown hook

ServerApp.shutdown() stops HTTP admission, then the schedule service, then the job scheduler, then the authenticator, then the cancellation registry and profilers, then closes Ignite, then cancels local executors. A source comment explains why this is not a JVM shutdown hook: the JVM runs hooks concurrently with no ordering guarantee. NodeApp.shutdown() is idempotent and never deactivates the cluster — stopping one node must not take the whole cluster offline.

Scheduling semantics that matter operationally

Lease-based claiming

A due occurrence is claimed by an entry processor that writes claimUntil = now + 60s. Another claimant seeing a live lease backs off. Multiple API-server processes can therefore run schedule pollers safely.

The owner id is a random per-process string used only for lease ownership, not liveness.

Misfire policies

  • FIRE_ONCE — run the earliest missed occurrence.
  • SKIP — advance past everything missed, run nothing.
  • FIRE_LATEST — run only the most recent missed occurrence.

Cron schedules carry an IANA time zone.

Retry is separate from misfire

Misfire handles missed ticks. Retry handles a fired occurrence that failed: a job listener checks the schedule's maxRetries against a retry counter in the job metadata and resubmits with the counter incremented.

Two distinct mechanisms, easy to confuse.

Crash recovery needs a registered factory

Each job type must register a body factory so a job can be reconstructed after the owning process dies. An orphaned job whose type has no factory is marked FAILED during recovery rather than resumed.

At-least-once delivery

Schedule delegation is explicitly at-least-once, not exactly-once. Job bodies must be idempotent, keyed on schedule id plus fired timestamp. docs/jobs/ReadMe.md

Two enum-encoding traps this design exists to avoid

1. Ignite always writes an enum field as its ordinal(). Binarylizable and a registered serializer on the enum are silently ignored. So a persisted class must never hold a raw enum field — it holds a boxed Byte code with hand-written typed accessors. It must be boxed, not primitive: a primitive autoboxes to a non-null zero and defeats the data-loss detection.

2. A raw EnumSet must never be persisted, because its backing bit-mask is keyed by ordinal — reordering the enum would silently remap the entire set. Sets are stored as a sorted byte[] of codes instead.

Both rules are enforced by PojoComplianceEnforcerTest.

Data Access Layer

Two entirely separate access paths: Ignite caches for Phoenix's own state, and raw JDBC for the external systems of record. There is no ORM anywhere.

Path 1 — Ignite cache access

Phoenix's own state. Direct IgniteCache calls, no transactions, optional SQL over indexed shell columns.

Path 2 — external JDBC

Systems of record. Templated SQL compiled with an injection guard, executed through a per-host slot budget of pools.

Path 1 — Ignite cache access

  • No repository or DAO layer in the conventional sense. Services and compute tasks call IgniteCache directly. The nearest thing to repositories are the Security Master's SecurityMasterDataRepository and OverridesRepository, which wrap its eleven-cache generation set.
  • No transactions. Every cache is configured ATOMIC, not TRANSACTIONAL — so there are no transaction boundaries to document. Atomicity where it matters is achieved with single-key primitives instead: putIfAbsent for computation ownership, and javax.cache entry processors for schedule claiming. An entry processor executes server-side on the key's primary partition, which makes a read-modify-write atomic without a transaction.
  • SQL over caches is available through Ignite Calcite on the indexed, @QuerySqlField-annotated columns of Tier 2 shells — used for data-catalog lookups. This is why Tier 2's “generated, never hand-written” rule matters (see Data Model & Cache Catalog): a hand-written shell can let the SQL columns drift away from the Protobuf payload they are supposed to mirror.

Path 2 — external JDBC

Query compilation — SqlQueryTemplate

A data item's stored SQL is a template. The compiler:

  • Accepts only $start, $stop, $token and ${token} references.
  • Rejects any Velocity directive outright — #if, #foreach, #set, #parse, #include, #macro, #evaluate and the rest — via an explicit pattern. This is a deliberate injection guard.
  • Renders $start and $stop inline as quoted ISO dates (they come from a CompactDate, so they cannot carry arbitrary text).
  • Turns every other token into a ? JDBC bind marker, and validates each marker's placement — not inside an identifier or a literal, with quotes balanced.

src/main/java/com/clarifi/phoenix/ashes/common/query/SqlQueryTemplate.java

Connection management — BoundedDatabasePoolRegistry

Not one pool, but a slot budget per database host, holding a small pool per (user, source) pair so that queries run under the requesting user's own database credentials. Acquiring a data source follows a documented four-path state machine:

  1. Fast path
    A pool for this user and source already exists — increment its loan count and return.
  2. Open-slot path
    The host has a free slot — create a new ManagedPool and consume the slot.
  3. Eviction path
    No free slot — evict the least-recently-used idle pool and take its slot.
  4. Wait path
    Nothing evictable — block for up to five seconds on a slot-freed signal, then retry.

Connection discipline

Connections are opened read-only with a 30-minute maximum lifetime. A DatabasePoolLease records the exact pool identity it borrowed from, so a caller cannot release against a mismatched pool, and a compare-and-set makes release exactly-once.

Limits and visibility

Production limits are 50 connections globally and 100 per user, from dataLoading.*. Per-pool timing histograms feed the database-connections monitoring page.

A simpler path also exists

JDBCDataConnection uses DriverManager.getConnection directly with no pooling, for one-off catalog query execution.

Caching is not an optimisation bolted onto Phoenix — it is Phoenix. There are five distinct caching layers, and they behave differently.

Read the table by column: what each layer holds, how an entry is addressed, what makes it go away, and what consistency you actually get. The layers are independent — a stale answer in one says nothing about the others.

Messaging & Eventing

Asynchronous coordination in Phoenix is real, but nothing behind it is a message broker — every event path is built on Apache Ignite primitives. Knowing the four that exist tells you exactly how a change on one node becomes visible on the others.

There is no message broker

No Kafka, ActiveMQ, RabbitMQ, SQS or JMS — no such dependency appears in the build, and no producer, consumer, topic or queue configuration exists. Any documentation claiming Phoenix uses a broker would be wrong.

The equivalent of a topic subscription here is a continuous query: a listener registered on a cache that fires when matching entries change.

Login sequence

  1. Client posts credentials
    POST /api/login with an Ion body of {username, password}.
  2. LoginHandler calls validateCredentials
    The handler delegates to the configured authenticator — OktaAuthenticator in the dev and production configuration.
  3. Password grant against Okta, then local JWT validation
    The authenticator performs the password grant against Okta and receives a JWT, which it validates itself: signature via the JWKS key matching the kid, audience, subject and expiry.
  4. createUser resolves the permission set
    Group → roles → permissions.
  5. register(user) into the cluster
    UsersService writes the user to AuthenticatedUsers under both the token id and the user id.
  6. 200 back to the client
    The token is returned in the body and as an HttpOnly PHX_AUTH cookie (1 h).
  7. Any later request
    The client presents X-Auth-Token or the cookie; UsersService runs validateAndTouchToken(token, idleTimeout), which refreshes last-access.

Per-request enforcement — AuthMiddlewareHandler

  1. Assign a request id
    A monotonically increasing id goes into the Log4j 2 thread context, and is snapshotted onto the exchange so asynchronous continuations keep it. This is what makes [rq#…] appear in the API log pattern.
  2. Default-deny gate
    Anything not under /api, /api-legacy or /admin, and not in the public exact or prefix lists, gets a bare 404 — deliberately, to avoid confirming what exists to a prober.
  3. Bypass for login and logout
    /api/login and anything starting /api/logout skip the token check — otherwise you could never authenticate.
  4. Resolve and validate the token
    Header X-Auth-Token first, then the PHX_AUTH cookie. Must parse as a UUID. Validated cluster-side by UsersService, which also refreshes the idle timestamp. Missing, unparseable or expired → 401.
  5. Permission checks
    An empty permission set → 403, except for /api/version. Any /admin path additionally requires ADMIN_READ → 403 otherwise.
  6. Attach and forward
    The authenticated user is attached to the exchange and the request proceeds into the rate limiter, then the route.

Two-layer authorization

Layer 1 — middleware

Uniform and blunt: non-empty permissions everywhere, ADMIN_READ for /admin.

Layer 2 — in-handler

Individual handlers check finer permissions in code. Confirmed examples:

  • Baskets require WRITE to create or delete, and ADMIN_BASKET for cross-user operations.
  • Schedules require WRITE to create, and ADMIN_DELETE/ADMIN_WRITE to delete another user's.
  • Data sources require ADMIN_WRITE to mutate and SYSTEM_LOCKS to lock.
  • The Security Master rebuild requires ADMIN_WRITE.
Not established: the complete per-operation permission mapping

The full mapping for the users, groups, roles, configs, admin-task and message-of-the-day handlers is not established. They reference permission constants but were not exhaustively traced. Verify in the handler before relying on a specific grant.

Token lifecycle

  • A token is a random UUID minted at login and stored on the authenticated user. It is not a JWT — the Okta JWT is consumed during login and not reissued to the client.
  • Validation is cluster-side, so any API-server instance accepts a token issued by any other. The API tier is genuinely stateless.
  • Idle timeout is 12 hours in the shipped configuration, refreshed on each request.
  • A token whose user still has an active data session is not evicted even when idle-expired — long computations do not lose their owner.
  • Logout resolves the target user id from header, then cookie, then path, then query, then body, in that order.
Service-to-service authentication

There is none in the conventional sense, and that is by design: the API server and the data nodes are members of one Apache Ignite cluster and trust each other at the cluster level. Node-to-node security is therefore a network/deployment concern, not an application one.

Not established from source: whether TLS is enabled on the Ignite discovery and communication channels in any environment — the shipped YAML does not configure SSL for them.

Potential areas for review

Each of these is a factual description of the implementation. None is asserted to be exploitable.

Potential area for review 1. Local authenticator accepts any password when none is configured

LocalFileAuthenticator treats a user with no passwords.json entry as accepting any password, and an unknown username falls back to a synthesised demo user. The shipped dev and prod configuration uses Okta, so this is development behaviour — review if local is ever enabled elsewhere. See Authentication & Authorization for the provider table.

Potential area for review 2. Emergency admin CLI has no authentication or dry run

JsonAdminCli connects over the thin client and can overwrite any Tier 2 cache entry. Its import replaces rather than merges — fields absent from the JSON reset to defaults — and it bypasses business validation. The repository's own index already flags it as an emergency escape hatch, not a routine path. Control is by network access to port 10800.

Potential area for review 3. Three one-hour Undertow timeouts

idleTimeoutMillis, noRequestTimeoutMillis and requestParseTimeoutMillis all default to one hour. docs/timeouts-and-thread-pools.md raises this itself as a slow-loris consideration and a source of load-balancer mismatch.

Potential area for review 4. Cluster transport encryption not established

The shipped YAML configures no SSL for Apache Ignite discovery or communication. Node-to-node traffic therefore appears to rely on network isolation. Not established from source whether TLS is applied at the infrastructure layer — the separate infrastructure repository may handle it.

Potential area for review 5. A passwords.json ships on the classpath

src/main/resources/security/passwords.json exists, and unlike the per-environment security folders it is part of the packaged resources. Its contents were deliberately not read for this document. Worth confirming what it contains and whether it should ship in a production image.

Potential area for review 6. Cookie and token lifetimes disagree

A fixed one-hour cookie maximum age against a twelve-hour server-side idle timeout. Not a weakness in itself, but the mismatch makes session-expiry behaviour hard to reason about. See Data Lifecycle.

Overall impression

The security posture is notably deliberate: default-deny routing, read-only data access under per-user credentials, a genuine injection guard rather than string concatenation, active dependency management with documented CVE rationale, secret masking in several independent places, and peer class loading disabled. The items above are worth confirming, not alarming.

Error Handling

Every status code Phoenix returns is chosen by the handler that returns it, so there is no single place to look up error behaviour. If you are writing a client that parses errors, the map and the exceptions below are the contract.

There is no global exception mapper

No Spring @ControllerAdvice equivalent, and no Undertow ExceptionHandler wired into the chain. Status mapping is a convention, implemented per handler. That convention is mostly followed, but not universally — documented honestly below.

The shared convention

HandlerUtils provides notFound(), badRequest(), forbidden(), methodNotAllowed(), internalServerError() and notModified(), all delegating to a single errorResponse that sets the status and writes a Gson-serialised ErrorResponse — a one-field envelope.

{"error": "…"}

Where the convention is not followed

RateLimitHandler

Hand-builds its 429 JSON body rather than using the shared envelope, so it carries an extra retryAfterSeconds field.

LogoutHandler

Returns plain-text bodies for 400, 404 and 200.

SwaggerHandler

Returns plain text for 401.

Data-library handlers

Set StatusCodes inline for 404, 409 and 429.

These are factual observations of inconsistency, not defects — each response is well-formed. They matter if you are writing a client that parses error bodies uniformly.

  2. Is it the request or the cluster?

  3. Get the request id
    Grep the API log for [rq#<id>]. Everything on the request's own thread shares it.
  4. Follow it to the session or job

Performance & Scalability

Everything here is inferred strictly from evidence in the repository. No throughput or latency claim is made, because the repository contains no benchmark results.

What is designed to scale

Horizontal The API tier

Genuinely stateless. Tokens are validated cluster-side, so any instance serves any request. The Podman profiles run multiple API containers. Scaling out is adding instances behind the load balancer.

Horizontal The data tier

Partitioned caches with two backups and rendezvous affinity. Adding a node redistributes partitions and adds both memory and compute. Compute follows the data automatically because jobs are mapped by affinity.

Core design Colocated computation

The single biggest performance decision: TransformOrchestratorTask sends the computation to the node owning each issue, and only partial results travel back. The linked-basket loader carries an explicit comment that nothing large crosses the wire.

Memory discipline Packed binary representations

20- and 23-byte binary series keys, dates in a single char, values in packed arrays rather than per-cell objects, unit of account in a packed int, Tier 3 bit-packed dictionaries, string compression in the Security Master, on-heap caching disabled. Memory is treated as the scarce resource throughout.

Backpressure Admission control before work

The data-export handler checks remaining job capacity and rejects with 429 before validating or loading. Rate limiting, per-user session caps, basket concurrency limits and Security Master request limiters all sit in front of expensive paths.

Non-blocking waits Async polling

Session readiness polls with an asynchronous cache read rescheduled on the IO thread, backing off from 50 to 250 ms — no worker thread is held. Results stream to the socket through a reused direct buffer with no intermediate JSON tree.

Bounded resources

Scaling considerations worth knowing

  • The compute proxy is a cluster singleton. Every arbitrary-callable submission from every API server funnels through one node. Deliberate — the pending-handle map must live in one place — but it is a single point of both contention and failure.
  • Job-progress events are broadcast, not filtered server-side. A thin client cannot deploy a remote event filter, so every API server receives every progress event and discards the ones it does not want. Fine at current scale; worth remembering.
  • Security Master is replicated, not partitioned. Every node holds the full universe — about 15.5 GB in production. That buys fast local lookups at the cost of per-node memory that does not shrink as nodes are added.
  • Replicated caches do not scale by adding nodes. ACL, catalog, baskets and currency caches are replicated; adding nodes adds read capacity but not capacity for more data.
  • Rebuild is a whole-universe operation budgeted at up to 50 minutes. It is not incremental.
  • Unbounded polling loops. docs/timeouts-and-thread-pools.md records that the cluster-active wait loops in ServerApp, NodeApp and AdminApp sleep and retry with no upper bound, so they can spin indefinitely against a cluster that never comes up.
  • A known O(n²) scan. The point-in-time export sender performs a per-as-of-group scan and its row order depends on hash-map iteration (PIT-15, rated Low).
What cannot be established

There are no benchmark results, load-test reports, SLOs, capacity models or production metrics in the repository. A load_test.py and a :common:performanceTest task exist, but no recorded output. Any statement about actual Phoenix throughput or latency would be invention.

Capabilities Not Present

Some capabilities a reader would reasonably expect in an enterprise platform genuinely do not exist in Phoenix. This section records those absences and names what serves the equivalent role instead, so nobody spends a morning looking for code that was never written.

Each entry below is an absence confirmed against the codebase, not a gap awaiting implementation. Treat any document that describes one of these features as describing a different system.

File processing

Phoenix has no user-facing file upload or download

No multipart upload handler, no object-storage document store, no virus scanning, no temporary-file lifecycle, no attachment model. S3 is used only as an Ignite node-discovery registry, not as a data store. If a document mentions a file-upload feature, it does not exist in this codebase.

Files do appear in four narrower roles.

RoleWhat it isLifecycle
Node-local cache files The largest file usage by far. Bulk segment payloads are written to a configurable disk path with memory-mapped regions — localCache.diskPath supports {appName}, {home}, {tmp} and {ignite} placeholders, with a 256 KB write buffer and up to 512 mapped regions. Managed by LocalCacheImpl; cleared by ClearLocalCacheTask and backfilled to peers asynchronously.

Bootstrap manifests and basket files YAML manifests under src/main/resources/{data-items,baskets}/manifests/ and tab-separated identifier files for static baskets. Read once by the bootstrap tooling; filtered by environment and stage.

Search

There is no search engine

No Elasticsearch, Solr, OpenSearch or bare Lucene. No index definitions, no indexing pipeline, no reindexing job, no search cluster. The capability that users would call “search” is served three other ways.

1. Security Master token index

A purpose-built in-memory index (sm[token_index]) supporting lookup by identifier token and value, with exact or pattern matching. SecurityMasterServiceImpl.getIssueIds(pattern, attributeId, exactMatch) runs entirely on the node against the custom-binary dictionaries. This is the highest-volume “search” in the system.

2. SQL-indexed cache queries

Data-catalog caches are declared with SQL indexing enabled, so Ignite Calcite can query the @QuerySqlField columns of their Tier 2 shells. This backs data-source and data-item lookup by name.

3. In-memory filtering

GET /api/dataLibrary filters by name, category, source, frequency, visibility, point-in-time flag, symbolisation and currency-convertibility. The criteria model — SearchCriteria.SearchScope — enumerates 17 searchable scopes, with operators CONTAINS, STARTS_WITH and EQUALS. Apache CXF's FIQL extension is on the classpath for filter-expression syntax.

Reindexing, index recovery and search-cluster failure are therefore not applicable concepts here. The equivalent recovery action is a Security Master rebuild.

Other absences, covered in their own sections

Recorded here only as pointers — the detail lives where the subject does.

No message broker

Eventing is built on Apache Ignite primitives instead — see Messaging & Eventing.

No ORM and no relational database of Phoenix's own

The schema is the set of Ignite caches — see Data Model.

No single-page application

The UI is a small set of server-rendered pages with no frontend build — see Frontend.

Troubleshooting Guide

Organised by symptom, so you can start from what you observed rather than from what you suspect. Every cause listed is grounded in something actually present in the repository — no speculative advice.

Each entry has the same shape: the symptom in the summary, then the likely location, the first check that localises it fastest, the trace of causes and diagnostic steps, and the source the entry rests on.

Startup failures

The API server will not start

Likely location

The API server's startup path, before the socket binds: OpenAPI fragment assembly, the cluster connection, the authentication provider, or the trust store.

First check

Look for an IllegalStateException in the startup log before the socket binds. A malformed OpenAPI fragment is the single most likely cause of a boot failure after an API documentation change.

CauseHow to tellFix
A malformed OpenAPI fragment An IllegalStateException during startup, before the socket binds. OpenApiStartupAssembler validates every .json and .ion file under src/main/resources/swagger/ and refuses to boot on a syntax error or an unresolvable $ref. Fix the fragment. This is the single most likely cause of a boot failure after an API documentation change.
Cluster unreachable The startup retry loop logs repeatedly; /ready never turns 200. Note the loop has no upper bound and will retry indefinitely. Check node health and the discovery configuration. Remember the server needs the cluster even to authenticate anyone.
Cluster inactive Connected but waiting for ACTIVE. In production autoActivate is false by design. Run node/activate.sh.
Unknown authentication provider IllegalStateException at provider construction authentication.provider must be local, database/expressfeed/xpressfeed, or okta.
Trust store missing A warning from verifySslTrustStore(); Okta or Zscaler TLS then fails Run truststore/generate-keystore.ps1.

Source — OpenApiStartupAssembler, src/main/resources/swagger/, node/activate.sh, truststore/generate-keystore.ps1.

A data node will not start or will not join

Likely location

Node discovery, port allocation, data-region sizing, or the storage path.

First check

The node log's DEBUG partition-exchange and preloader loggers. A node that appears hung at startup may simply be rebalancing.

CauseWhat is happening
Discovery S3 in dev, staging and production; multicast locally. An S3 permission or bucket problem prevents joining outright.
Port collision Discovery uses 47505 with a range of 4; the client connector uses 47500–47504 with a per-node offset. Running several local nodes without distinct --nodeId values collides.
Rebalance wait cachesCheckpoint() deliberately blocks until every cache is fully rebalanced. A node that appears hung at startup may simply be rebalancing — the node log's DEBUG partition-exchange and preloader loggers will show it.
Data-region sizing Regions total around 20 GB in production. If the host cannot back that, startup fails. There is a hard 10 MB floor per region.
Storage path With persistence enabled the work directory is <storagePath>/<appName> and must be writable.

Source — cachesCheckpoint(), the node discovery configuration, --nodeId, <storagePath>/<appName>.

HTTP responses that look wrong

API returns 401 or 403

Likely location

A 401 is about the token itself; a 403 is about the permission set the user resolves to.

First check

GET /api/session. If that works, the token is fine and the problem is permissions.

401 — causes

  • No token presented — check the X-Auth-Token header or the PHX_AUTH cookie.
  • Token is not a valid UUID — a truncated or mangled value.
  • Token expired or evicted — 12-hour server-side idle timeout… but the browser cookie expires after only 1 hour, which is the usual cause of “it logged me out early.”

403 — causes

  • Empty permission set — the user resolves to no roles. Check the Groups and Roles caches, not just the Users cache.
  • An /admin path without ADMIN_READ.
  • A finer per-handler permission: WRITE, ADMIN_BASKET, ADMIN_WRITE, SYSTEM_LOCKS.
  • Failed login credentials — LoginHandler returns 403, not 401.

Diagnostic order

Likely location

Two different mechanisms produce this: the per-user rate limiter, and the job engine's capacity check.

First check

Before your first production change

Five things that will bite you
  1. You cannot remove or rename a persisted field. Not with a good reason, not with a migration you wrote yourself. Deprecate and escalate.
  2. You cannot create a cache outside Caches. ArchUnit will stop you, and the workaround you are thinking of is explicitly named and banned.
  3. You cannot renumber an enum. Reorder freely; never touch a code.
  4. A @ComputePayload schema change requires a full cluster restart. Not build-enforced — a rolling upgrade with mixed payload shapes crashes nodes mid-rollout.
  5. Never run the golden-fixture generators in CI, and never hand-edit a .bin.

Then: run testPersistence and the targeted tests; update the affected documentation in the same change (the repository requires this); write a Conventional Commits message; and if your change touches persistence, cluster lifecycle, authentication, security or deployment, ask for architect direction first — AGENTS.md says so explicitly.

A closing observation

The hardest thing about Phoenix is not any individual subsystem — it is that the distributed details are where the meaning lives. Which process is running this code? Is it a thin client or a cluster member? Does this object cross a wire, and if so which annotation governs it? Will this survive a restart? Almost every non-obvious piece of the codebase is an answer to one of those four questions.
